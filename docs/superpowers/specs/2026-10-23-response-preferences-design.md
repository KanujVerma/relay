## Product behavior

General remains the default and automatically follows the current question, coding stage, user attempt, engineer feedback and feature-design stage. No mode choice is required before Start, Ask or Help. No new model request chooses a mode. No speech-model/detector selector appears in normal UI.

Add a Responses section to existing Settings. It offers General (automatic), Coding discussion, Feature discussion, and at most eight named custom guides. General uses the existing behavior. The two optional built-ins bias organization within the actual task: coding discussion emphasizes clarifying inputs/invariants, supplied attempts and requested implementation; feature discussion emphasizes the current users/requirements/flows/tradeoffs/validation stage. Neither forces a complete solution or changes supported task facts. An explicit current question takes priority over the guide.

A custom editor has name, optional focus (automatic/coding/feature), and a bounded guidance textarea, with Save and use, Cancel and Delete. Editing alone changes no live behavior. A small character/byte-limit error is local and truthful. The main Home/Ask/live flow stays unchanged except an optional quiet current-guide label linked to Responses. It never blocks on a mandatory chooser. Settings explains that changing/removing a guide stops responses using it and that asking again uses the new guide. There is no automatic resubmission or draft/basis rebasing. Files and personal background link to existing My Context, with no second upload route.

Guides influence generated suggestions. Reviewed reference cards and exact approved-personal rendering retain their existing wording and authority. UI can say Guidance supplied for an actual generated answer; it must not claim the model followed every instruction or verified a fact.

## Existing behavior and evidence

At the frozen base, `ConversationContext._kind_of` already selects coding, case_study or discussion locally. `snapshot` derives the current stage and preserves current supported constraints, user attempt and engineer feedback. `tests/test_contextual_scenarios.py` already exercises a multi-turn engineer coding task and users→requirements→flows→tradeoffs→validation case study with exactly one mocked generation per accepted question. Existing unresolved/missing information remains explicit.

`generated_answer.make_prompt` currently contains current/semantic request, task/dialogue, role/job context and optional actual screen/text context; it has a 32 KiB total bound. The system policy currently says all input strings are data rather than instructions. Merely appending a custom-text field would therefore be a nonfunctional feature. This proposal introduces an explicit trusted policy allowing a narrowly defined low-priority response preference field, while all other data retains its existing interpretation. Guide text never enters task constraints, personal evidence, role/job approvals or account/provider configuration.

The REA client evidence and pinned OSS comparison are in [the research note](../../research/RESPONSE_PREFERENCES_RESEARCH.md). No competitor code/prompts/assets or external runtime SDK is adopted.

## Approaches considered

| Approach | Benefit | Cost and decision |
| --- | --- | --- |
| Immutable per-request optional preference, on existing ordered helper channel | Keeps existing native request authority and worker; captures one exact version before optional context waits; easy to prove no late attachment | Requires a small strict staging/retirement provider and host-owned use metadata. **Recommended.** |
| Put preference text into native audio/user-question envelopes | One object carries everything | Changes accepted audio/controller/native request schemas and request factories for presentation-only data. Unnecessary scope. |
| Mutable helper-wide prompt or restart helper on every change | Small initial API | Late changes can alter old requests, held EOU/image ordering is ambiguous, or normal Settings changes unnecessarily reap active audio/account/profile. Reject. |

Aider's two-pass architect/edit path and LibreChat's broad model/endpoint/tool presets are unsuitable runtime dependencies for this small native feature. We reuse Relay's existing coordinator, ordered transport, prompt, QA and protected storage instead.

## Exact preference and disk schema

All serialized schemas reject unknown keys, duplicate keys, boolean-as-integer values and invalid UTF8/control characters. Text allows ordinary newline/tab only; no truncation or silent normalization. Names are at most 64 UTF-8 bytes and nonblank. Custom guidance is at most 2,048 UTF-8 bytes and nonblank. A guide has a random UUID ID and focus enum `automatic|coding|feature`. At most eight custom guides; total encoded catalog at most 32,768 bytes.

Encrypted catalog schema1 has exactly `schemaVersion`, `catalogRevision` (UUID), `selected` (one built-in ID or existing custom UUID), and `guides` (array of exact `id,name,focus,guidance` objects). Built-in IDs are fixed `general|coding|feature`, not arbitrary strings. Duplicate IDs, missing selected IDs and oversize catalogs fail validation. Built-in text is original fixed Relay policy, not copied from Cluely/Aider. A native activation gets its own fresh opaque preferences revision UUID; a saved catalog ID/revision cannot confer permission or resurrect an old helper scope.

Reuse **root-accepted 194be02bcde8fcc34b009a6bb9f6c15db938dd31** `ProtectedSnapshotStorage` / `ProtectedSnapshotVault`, rather than reimplementing crypto or reusing the profile/account key. That accepted dependency is not yet part of this frozen base; root must reconcile it before implementation changes its fixed purpose cases.

Proposed fixed purpose values for approval:

| Item | Exact value |
| --- | --- |
| Directory | Existing user Application Support parent / `Relay/ResponsePreferences`, native-selected, no user-supplied path |
| Ciphertext file | `preferences.relayvault` |
| Authenticated header | `RELAYPREFERENCES1\n` |
| Keychain service | `com.relay.response-preferences.v1` |
| Keychain account | `local-response-preferences-aes256` |
| New fixed enum cases | `ProtectedSnapshotPurpose.responsePreferences`, `KeychainKeyPurpose.responsePreferences` |
| Nonsensitive preferences | `useSavedResponsePreferences`, default false, plus `committedResponsePreferencesRevision` (opaque catalog-receipt UUID); no guidance/name/guide ID/credentials in defaults |

Use accepted ciphertext-only atomic AES-GCM snapshot writes, exact directory owner/mode 0700 and file 0600 checks, no recursive ancestry creation/permission repair for this new domain, no symlink/hardlink acceptance, no key replacement/enumeration/cloud synchronization. The 32 KiB catalog bound is narrower than the reused vault's 8 MiB bound. Profile/account/history formats and keys stay unchanged. This protects stored bytes, not secure erase/backups or isolation from other processes running as the user.

Construction, ordinary rendering/typing, General default and fixtures do no disk/Keychain/helper/model work. Opening Responses is an explicit local read of the existing catalog; missing storage shows the empty editor without creating a key. Save and use is the only action that may create a new key/file. Root explicitly amended this to include an explicit Use action for Coding or Feature: it may create the first empty protected catalog/key. Rendering, typing, ordinary preparation and General remain inert; missing remembered storage still cannot be created silently. Later writes use existing-only keys. A remembered non-General choice sets its opaque committed catalog revision and then the enabled flag only after a successful, still-owned actual save. On the next explicit Send/Start, restore an existing catalog/key and require that authenticated catalog revision to match the committed receipt before native request issuance. A stale successful disk write with a different revision can therefore never activate on restart; report that mismatch and offer explicit local recovery or General. Missing/corrupt/locked remembered data reports an actionable error and preserves draft/basis; it neither creates a new vault nor silently claims the selected guide is active. Use General disables the remembered flag synchronously, retires the old guide, and is available even when the catalog/key cannot be opened. Settings can still open the saved catalog later to recover/edit it.

Native catalog/editor data may remain bounded in memory after an explicit read, just like the visible editor; it is never logged. Closing a conversation retires all helper/request copies. Deleting a guide removes it from the next successful encrypted snapshot and native catalog; no secure-erasure promise. Ordinary Settings Cancel preserves the previously committed selection and does not send editor text anywhere. Use General also retires the original owned preparation/save intent before any delayed completion can re-enable the remembered flag; actual started storage calls still join before another operation is available.

## Preparation and concurrency ownership

`@MainActor ResponsePreferencesCoordinator` owns editor/catalog state, a fresh activation revision, explicit read/save flights, and a maximum of eight original request-use records. Proposed public commands: `open() async`, `saveAndUse(draft:expectedCatalogRevision:) async throws`, `useBuiltin(_:) async throws`, `useGeneral()` (synchronous local retirement), `delete(id:expectedCatalogRevision:) async throws`, `prepareForExplicitAction(intentID:UUID,isCurrent:@escaping @MainActor ()->Bool) async throws`, `cancel(intentID:)`, and `waitForQuiescence() async`. Constructors and snapshot reads are inert. `prepareForExplicitAction` runs in the original owned Start/typed preparation, after actual account readiness and before native request stamping; it never starts a helper or changes account identity.

One actual read/write call runs at a time. Work is cancelled by original operation ID, never an unscoped delayed callback. Cancellation of a wrapper does not prove synchronous Keychain/storage work finished: busy remains until the actual call returns. Save and use first validates and writes while the previous committed guide remains active; only a successful still-owned storage receipt may then retire the previous revision, enqueue its retirement and activate the new guide. A failed pre-commit write leaves the previous selection active. A stale completed save may leave its successfully committed encrypted file on disk, but cannot change the native selection or committed-revision receipt; an existing-only restore rejects that mismatch rather than activating it. Owned serialization must finish before a later save/load/replacement starts. Compare expected catalog/editor revision, preserve newer edits, and require an explicit later Save rather than rebasing automatically. No callback or external/session lock is acquired while holding a storage/metadata lock.

The existing `ConversationOwnerBox` remains the only current helper/scope owner. No new mutable authority shadow is introduced. Preference lookups/retirement/publication checks run on MainActor and do not take a new lock inside `authority.withCurrentLease`. Native/background failure first retires the existing original authority; later MainActor cleanup fences the exact original owner. Old guide IO/callbacks cannot close or change a replacement conversation.

## Immutable request snapshot and wire contract

The linearization point is the first app-owned ordered ingress claim of the genuine native request, before optional screen/text/image capture awaits. At this point capture one immutable activated preference version. Explicit typed requests are stamped only after readiness; automatic requests use their genuine native EOU identity. No fake audio, source, event sequence, consent or lease is introduced. Subsequent Settings changes cannot mutate that captured value or attach text to a request that already reached the helper.

General needs no additional frame. A non-General offer uses one strict `response_preferences` JSON frame, outside the OCR context-frame array, queued immediately before the original native question envelope in the same existing bounded writer. Exact fields: `schemaVersion:1,kind,captureSessionID,sessionEpoch,presentationGeneration,requestID,eventSequence,preferencesRevision,focus,guidance`. The five original identity fields match the genuine request and the currently open capture/assistant namespace. `preferencesRevision` is an opaque UUID; text is never a capability. Existing 16 KiB frame and 32-frame/256 KiB queue limits stay unchanged. No hundreds-frame queue or additional process/worker.

The helper stages at most eight offers and keeps a bounded 512-entry replay/retirement ledger per actual helper lifetime, without retaining old guidance text. Exact repeats do not create a second use; changed UUID/payload reuse fails closed. Staging grants no question/account/source/model authority. Only actual accepted native request admission can claim the exact original offer once. Late/wrong-scope/wrong-epoch/wrong-generation offers cannot attach to active work; ordinary no-offer admission remains General. Unclaimed offers expire two seconds after actual staging; admission checks this deadline before use, and one owned earliest-deadline timer removes expired text even while stdin is idle. The timer is bounded by the eight slots and is cancelled/cleared on scope close; old timer callbacks compare original slot identity before removal. Expiry does not extend the native request deadline. Exhausting the fixed ledger rejects further offers rather than evicting replay ownership or extending the queue. Close/EOF drops all staged/use records.

A strict `response_preferences_retired` frame has exactly `schemaVersion:1,kind,captureSessionID,sessionEpoch,preferencesRevision`. It retires only that original scope/revision, including staged offers before EOU and when there is no active answer. An old-scope/revision retirement cannot clear newer preferences or a replacement. Valid retired offers cannot be restaged by a late callback. Malformed data rejects the transport rather than being interpreted as settings/account permissions.

## Live change, cancellation and publication

At activation after an owned successful save, when selecting a built-in, or when selecting General/deleting the active guide, retire the previous native preference revision before making the new selection available. Unsaved edits and failed writes do not retire it. It then **synchronously enqueues** matching helper retirement before guide cleanup or cancellation callbacks that can release a held EOU/PNG. If that channel fails, withhold held question release and use existing owned helper-failure/reap behavior. Never silently flush an old guide after its retirement.

Before actual native admission, retirement clears only optional guide data; a still-current original question can genuinely fall back to General once. If a generated request already consumed the guide, cancel/fence its actual dependent work and suppress its answer. There is no second text/model attempt after a POST. Account/credential awaits use the same original base request predicate plus the exact guide-use predicate before POST and after awaits. The original base-current predicate is independent of the preference-use predicate, preventing recursive permit-to-current checks. No new boolean/reflection/account identity or permission receipt is accepted from guidance. The one existing generation budget and serial worker remain unchanged.

The host, not model output, may add `responsePreferencesRevision` to generated-answer provenance only when it actually supplied that exact version to the prompt. This is optional alongside existing taskContext metadata; both can coexist. Reviewed reference/personal-only answers omit it. Native strict parsing supports only that explicit optional UUID field; no wire-wide migration or arbitrary provenance object. The model output schema continues to reject self-issued provenance/use metadata.

On a result carrying a used revision, final MainActor publication verifies the original current owner, original request/basis, native lease, current preference-use revision, and any actual OCR/image re-observation. The preference check is immediately before the synchronous native commit, with no await or new lock between them. Retired guide-dependent displayed cards clear; unused personal/reference/General answers remain intact. Settings activation never invents a new semantic question or silently retries. Stop, Pause, End, helper change and account/mode mutation retain existing retirement and actual close/reap joins; guide staging cannot reopen a closed owner. Scope quiescence makes no new claim about account-global refresh threads, which are still terminated at the helper-reap boundary for identity changes.

## Prompt and evidence boundary

Add a typed validated `response_preferences` prompt section with focus/guidance only. Names/catalog/other guides, identifiers, credentials and private source paths are not model input. The fixed system policy explicitly allows this section to influence response organization/level of explanation only below the current explicit request and existing policy. It cannot assert facts, replace task constraints, select provider/model/effort, grant file/screen/audio/network/account access, expand allowed code languages or approve biography. Host task projection/personal retrieval remains unchanged. The complete prompt must still fit 32 KiB; do not truncate supported task facts or silently claim an over-budget guide was supplied. Existing hard output limits and CardQA remain unchanged; unsupported/conflicting preferences may be ignored or withheld honestly. Current Python/SQL output support is not broadened merely by a custom language request.

Coding and feature discussion continue to use the actual local task stage, rather than one extra classifier call or two-pass architect/editor generation. Save/use/delete/preview performs no inference. Synthetic prompt-capture tests can prove which preference was supplied and which checks ran; they do not prove live model usefulness or instruction-following.
