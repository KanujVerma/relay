## Protocol and ownership

Visual request exact keys: `schemaVersion=1,kind=visual_input_request,requestID=UUID,action=verify|disable|status`. Response exact keys: `schemaVersion,kind=visual_input_response,requestID,action,resultRevision,status,reasonCode,model`. Status enum: checking/verified/disabled/unverified/cancelled/unavailable/busy. Reasons: checking/probe_verified/probe_unverified/probe_cancelled/user_disabled/current_status/inference_disabled/session_active/answer_in_progress/probe_in_progress. Checking is only verify revision1; every control has exactly one terminal revision2. Model is the actual configured OAuth slug or null, never an account identity. Validate schema, owned UUID/action and revision before removing a waiter. Exact replays may repeat the same latest state without IO; changed payload under an old UUID fails closed.

The native control wait budget is35 seconds, matching the backend's maximum30-second stream deadline plus bounded pipe slack. A verify terminal response represents actual probe-task completion/cleanup, including cancellation. While its waiter remains pending, block Start/Resume/AI-mode changes. Disable and End retire native reflection/image-offer authority synchronously before helper notification, then join actual control completion or existing helper shutdown/reap. A helper/configuration generation change retires all native reflections. Status is passive and never an implicit sign-in/probe; settings construction makes no request.
